# Educational review: anchored narration, gated diagrams, tool discipline

## Status: Decided — staged rollout; grounded against `7536961` (tip of the 09-review-fixes stack)

Originally drafted from the 2026-07-04 agentic-workflow analysis against `2cd7be7`, then
re-grounded and decided in the 2026-07-04 iteration session against the full implemented
spec stack (acp-migration, scoped-update-generation, comment-anchoring, concurrent-chat
all in the tree). The starting observation stands: **the section diagram is both overused
and not educational** — a symptom of three structural problems, not a prompt-tuning miss.

This spec spans schema, prompts, tools, and validation because the fixes only work
together: a better narration schema without tool discipline still produces repetitive
turns; tool discipline without anchoring still produces walls of text.

**All former open questions are resolved**; decisions are inlined in their sections and
indexed in the [Decision register](#decision-register) at the end.

## Staging (Decision: stage + re-measure)

The evidence below was collected under a structured-output pipeline that no longer
exists (see next section). Rather than tune behavioral enforcement against extrapolated
behavior, the work ships in two stages:

- **Stage 1 — structure**: schema v2, prompt rewrite, integrity-only validation
  (unknown files, unresolvable anchors, malformed edges), renderer, migration, the
  scoped-pipeline updates, and the tool-layer changes that are structural rather than
  policing (the `point` merge, `get_review_progress`, `edit_review` v2, channel-policy
  prompt rewrite, tool-description exclusions, resolve-note-as-reply).
- **Measurement gate**: generate several real reviews on the ACP engine and measure,
  from stored `annotations_json` and persisted actions: diagram fill-rate per review,
  repair-turn rate, block-anchor validity rate, caption-confetti incidence (blocks/
  section vs sentences/block), and channel duplication in chat/batch turns (prose
  restating a `point` target; `reply_to_comment` duplicating a resolve note).
- **Stage 2 — behavioral enforcement**, only for failure modes that survive
  measurement: the diagram budget merge cap, the file-inventory diagram drop, the
  caption-confetti warning, and host-level tool dedup.

## Evidence (what the stored reviews show)

All numbers from `annotations_json` across six reviews Limn generated during its own
development (37 sections).

**Provenance caveat (drives the staging decision).** All six reviews were generated by
the pre-ACP pipeline, where both engines had native output-schema enforcement: Claude
via the Agent SDK's `outputFormat: json_schema` (deleted `claude.ts:184`), Codex via
the app-server `outputSchema` turn param (deleted `codexAppServer.ts:474`). ACP has no
output-schema channel (`specs/acp-migration/spec.md:217-221`), so structured generation
is now schema-in-prompt + client-side zod + one repair turn (`structured.ts:74-80`,
`acp.ts:96,111`). The slot pressure changed shape: under constrained decoding the
sampler *had* to emit every key (filling with content is reflexive); now a key is
merely zod-required — omitting it burns the single repair turn, but writing `null` is
easy. Weaker overuse pressure, probably — but the 2/7 (claude) vs 6/6 (codex) diagram
gradient below existed *while both engines had enforcement*, so enforcement alone never
explained overuse. Hence: measure, don't assume.

**Diagram overuse is engine-correlated and was trending up.**

| review (id) | engine | sections with diagram |
| --- | --- | --- |
| 1 | claude | 2/7 |
| 2, 3 | codex | 3/4, 4/7 |
| 5 | codex | 4/6 |
| 6 | codex | 5/7 |
| 7 | codex | **6/6** |

Review 7 put a diagram on *every* section, including "Test Coverage"
(`Unit tests → Protocol helpers → UI states`) and "Review Artifacts"
(`Spec → Plan → Commits`).

**Diagrams falsely linearize.** The wire shape (`schema.ts:11-15`, flat node array)
plus the renderer (`kit.tsx:84-90` — `DiagramNodeBox` joined by a `→` `Flow` arrow)
can express exactly one structure: a linear chain. Stored examples of what that does
to non-linear content:

- `Claude → FakeEngine → Codex SDK → Codex app-server` — four **parallel** engine
  adapters rendered as a pipeline. Actively misleading.
- `Dropdown header → Delete row action → Bottom controls → Tool labels` — a list of
  UI tweaks dressed as a flow.
- Genuinely-sequential mechanisms (`Engine callback → Registry → Renderer IPC →
  Cleanup`) read fine — roughly a quarter of stored diagrams.

Diagram nodes are inert text: Limn has a full anchor economy (`FocusTarget`, the
`focus`/`tour` tools, clickable chips) and the diagram is the only surface that does
not participate in it.

**Schema fields the prompt never argues for go dead or reflex-fill.**
`plainNotes` is filled in **1 of 37** sections — and `buildReviewPrompt`
(`prompts.ts:50-97`) never mentions it; it exists only as a schema slot. Conversely
`diagram` is mentioned with zero criteria ("Optionally add", `prompts.ts:91`) and
reflex-fills.

**Narration granularity is fixed at the wrong level.** One `what` blob per section,
covering up to 8 files. Review 7's "Contracts And Persistence" narrates 8 files in a
single paragraph; the load-bearing design observation (per-chat-not-global mode) is
its final sentence; a concrete anchored finding (NUL separator making git treat
`approvals.ts` as binary) is buried mid-paragraph in another section where an
anchored comment belongs.

**Turn output duplication is mandated, not emergent.** `CHAT_TOOL_POLICY`
(`prompts.ts:16-23`) commands: "ALWAYS call focus", "add_comment when you spot",
"suggest_mark_viewed proactively", and "mention the location in prose only *in
addition to* focus, never instead of it". Jointly: say it in prose AND point AND
comment AND suggest — in one turn. The batch prompt (`prompts.ts:126-149`) bakes the
same in triplicate for a no-change comment: `reply_to_comment` ("answer it"), a
`resolve_comment` note ("whether or not it needed a code change", `prompts.ts:145`),
and a final "2-3 sentence summary" (`prompts.ts:148`).

## Design principles (the meta-rules this spec applies)

1. **Argued, grounded, checkable-where-cheap.** Every schema field must be (a) argued
   for in the prompt, (b) grounded in something the reviewer can click, and (c)
   mechanically checkable where a cheap check exists. A field failing (a) and (b) is
   cut. (`plainNotes` failed all three; `diagram` fails b and c today.)
2. **One turn, one primary channel.** Prose, pointing, comment-thread actions, and
   suggestions are channels; a turn picks the one that fits and uses the others as
   at-most-a-pointer. Never the same content in two channels.
3. **Structure over adverbs.** Where a behavior matters, make the redundant/degenerate
   combination inexpressible or unattractive (schema shape, tool merge, host-level
   rejection) rather than discouraged ("ALWAYS", "proactively" — the current adverb
   arms race). Post-ACP corollary: make the *sparse* output the path of least
   resistance — truly-optional fields are `.optional()`, so omission is cheaper than
   filling (and no longer burns the repair turn).
4. **Measure before enforcing.** Behavioral gates are tuned against post-ACP
   generations, not pre-ACP evidence (see Staging).

## Part A — Review output schema v2

### A1. Anchored narration blocks (replaces `what`; subsumes reading path, `plainNotes`, `insight`)

The core change. Section narration becomes an ordered list of prose blocks, each
optionally anchored:

```ts
// wire — zod is the sole validator now (schema-in-prompt); .optional() is allowed
// and used for fields whose absence is the common case
const wireAnchor = z.object({
  file: z.string(),
  side: z.enum(['new', 'old']).optional(),   // absent = 'new'
  line: z.number().optional(),               // absent = whole file
  endLine: z.number().optional()             // absent = single line
})
const wireBlock = z.object({
  text: z.string(),                 // 1–4 sentences of narration
  anchor: wireAnchor.optional()     // absent = framing/cross-cutting block
})
```

**Anchor shape (Decision: flat on the wire, `FocusTarget` in the domain).** The flat
shape exists *only* on the wire, because the schema now travels as prompt text and a
flat object is easier for a model to emit than an `anyOf` union — and every parse
failure burns the single repair turn. At parse time, `sectionFromWire`
(`schema.ts:90-102` — the one wire→domain seam both the fresh-generation and splice
paths share) normalizes every wire anchor into the existing `FocusTarget`
discriminated union (`tools.ts:42-56`), so the domain, renderer, stamps, and focus
pathway see exactly one anchor type — no second anchor schema (the invariant
`tools.ts:72` already guards for comments). `FocusTarget`'s `diff` arm gains an
optional `endLine` (shared with B1's range support). Normalizer rules, warn-and-degrade:

- no `line` → `{ kind: 'file', file }` (side/endLine ignored, warn if present)
- `line` present → `{ kind: 'diff', file, side: side ?? 'new', line, endLine? }`
- `endLine < line` → drop `endLine`, warn

`Section.what: string` is replaced by `Section.narration: NarrationBlock[]` in
`shared/types.ts:74-78`. Reading rules the prompt states explicitly:

- Blocks in order must read as **one continuous explanation** — anchors attach
  paragraphs to places, they don't replace transitions. (This preserves the one
  virtue of the monolithic `what`: it forces a narrative. Without this rule the
  failure mode flips from walls-of-text to caption confetti.)
- The order of anchored blocks **is the recommended reading order** — the model is
  told: "order anchored blocks in the order a reviewer should read the code, which
  is rarely alphabetical."
- Depth is variable by design: one block/one sentence for mechanical changes;
  several blocks for the core mechanism. Target 2–8 blocks per section.
- First block is typically unanchored and carries what `desc` carries today (why
  this section matters) — see A7.

What this subsumes (each was a separate proposal before collapsing into blocks):

- **Reading path**: an ordered list of anchored stops with notes *is* the block list.
  No separate `readingPath` field.
- **`plainNotes`**: a per-file note is an anchored block, inline in the narration
  where it gets read. Field deleted (1/37 fill rate; never prompted).
- **`insight`**: a caption without a diagram is currently expressible
  (`schema.ts:25`) and meaningless; caption folds into the diagram object (A2).

**Anchor stamps (Decision: mint now — the infrastructure landed).** comment-anchoring
is in the tree: `AnchorStamp`/`AnchorContext` live on `CommentAnchor`
(`shared/types.ts:109-125`) and `stampAnchor` (`anchorStamp.ts:106`) stamps agent
comments at creation (`tools.ts:222-227`). The merge step stamps block anchors,
diagram-node anchors, and hotspot anchors the same way, so drift mapping covers them
from day one instead of inheriting the rot problem. A block whose anchor maps to a
line valid in the file but outside every rendered hunk gets the existing
anchored-but-not-visible treatment (`notInDiff`, `shared/types.ts:152`): the anchor is
kept and clicking degrades to file-level focus.

Renderer implications (kept brief; UI detail is a follow-up spec):
`SectionView.tsx:104-127` (the diagram/`what` two-column block) becomes a narration
column where each block is a `Commentable` and clicking an anchored block focuses
the diff (reuse the focus pathway). The collapsed-section sub-line, which today shows
`s.what` (`SectionView.tsx:57-60`), shows the first block's text, CSS-truncated.
Bidirectional linking — scrolling the diff highlights the matching block — is the
eventual payoff but is **not** required for v1.

Drift synergy: block anchors make narration staleness *computable*. New commits
touching `approvals.ts:40-60` mark exactly the blocks anchored there as stale — flag
them in the UI, and the scoped update turn revises blocks, not whole sections. The
scoped patch schema reuses `wireSection` verbatim (`schema.ts:58-67`), so it inherits
blocks for free; a finer block-level patch stays future work (Decision 13).

**Alternative considered — keep `what` and add a separate `readingPath` field:**
rejected. Two fields narrating the same code drift apart, double the reflex-fill
surface, and the reading path would duplicate `what` in note form — exactly the
repetition problem this spec exists to fix.

**Alternative considered — per-file narration keyed by path (a `Record<file, text>`):**
rejected. Loses the narrative thread. (Records are technically expressible again
post-ACP, but the narrative argument alone kills this.)

**Alternative considered — `FocusTarget` union on the wire:** rejected for the wire,
adopted for the domain. An `anyOf` union in the embedded JSON schema is harder for a
model to emit from prompt text, and parse failures are expensive (one repair turn).
The flat-wire/union-domain split gets both: model-friendly emission, single domain
type.

### A2. Diagrams: typed, gated, anchored — the exception, not the garnish

The diagram stays, but earns its place:

```ts
const wireDiagram = z.object({
  why: z.string(),                  // one line: what this diagram shows that the
                                    // narration can't — the anti-reflex field
  caption: z.string(),              // absorbs today's insight.caption
  nodes: z.array(z.object({
    id: z.string(),
    label: z.string(),
    kind: z.enum(['plain', 'hi', 'new']),   // was ''|'hi'|'new' — '' member renamed
    sub: z.string().optional(),     // today required (schema.ts:14) → guaranteed filler
    anchor: wireAnchor.optional()   // clicking a node focuses the code
  })),
  edges: z.array(z.object({ from: z.string(), to: z.string(), label: z.string().optional() }))
})
// section.diagram: wireDiagram.optional()
```

- **Edges, not implicit chaining.** Fan-out/fan-in becomes expressible; the renderer
  lays out a chain exactly as today when edges form one, and stacks parallel nodes
  otherwise. Layout is a two-tier chain-plus-branches (Decision 5) — no dagre; the
  stored data has no diagram that needs more. **Defined fallback**: when edges form a
  graph the two-tier layout can't draw (a cycle, multi-level fan-in), the renderer
  degrades to the node list in array order with edge labels listed below — never a
  crash, never a false chain. Cycle detection is cheap and runs at merge (integrity,
  Stage 1) so the warning surfaces with the review.
- **Budget in the prompt (Stage 1):** "At most 1–2 sections in the whole review carry
  a diagram — only where a runtime flow or lifecycle is non-obvious from the narration
  order. Never render parallel alternatives, a file inventory, or a list of UI tweaks
  as a flow." (Names the two observed failure modes verbatim.) The *enforced* cap is
  Stage 2 (A9).
- **`why` is required when a diagram is present.** A one-line justification suppresses
  reflexive filling at near-zero cost. (Validation can only assert it non-empty — its
  value is friction, not checkability.)
- **Anchored nodes** join the anchor economy: click "Registry" → focus
  `approvals.ts`. Same wire anchor, same normalizer, same stamps as A1.
- **Validation** (A9): integrity gates in Stage 1; the budget cap and the
  file-inventory heuristic in Stage 2.

**Alternative considered — free-form Mermaid/text diagrams:** rejected; ungrounded
(nothing clickable, nothing checkable) and un-diffable across update passes.

**Alternative considered — a critique second turn ("which of your diagrams would you
cut?"):** deferred. Costs a full engine turn per generation; the `why` field plus
budget prompt gets most of the benefit free. Revisit at the measurement gate.

### A3. `was` / `now` behavior contrast

```ts
// on wireSection
contrast: z.object({ was: z.string(), now: z.string() }).optional()
```

One sentence each. The densest educational unit a review has, and models produce it
far more reliably as a named field than buried in prose. Prompt: "fill `contrast`
when the section changes observable behavior; omit it for pure additions or
refactors." Rendered as a compact two-row strip above the narration.

### A4. Hotspots as generation-minted agent comments — no new UI

The generation output gets a top-level field:

```ts
hotspots: z.array(z.object({
  anchor: wireAnchor,               // file required; line/range when known
  text: z.string(),                 // what to look hardest at, and why
  severity: z.enum(['risk', 'note'])
}))
```

(`'question'` was in the draft enum and is **cut**: intent questions already have a
home — the top-level `questions` field — and a second question-shaped slot re-creates
the channel ambiguity this spec exists to kill.)

The merge step converts each hotspot into an **agent-authored comment**: same shape
`add_comment` mints (`status: 'resolved'` — never queued into the user's batch,
preserving the `tools.ts:232` invariant), stamped via `stampAnchor` exactly as
`add_comment` now does (`tools.ts:222-227`) — the merge step calls `stampAnchor`
itself since it upserts directly rather than going through the tool impl. Hotspot
comments render in the existing comment UI: threadable, replyable, on the line.

**Lifecycle (Decision: resolved comments keep their action buttons — a general rule,
not hotspot machinery).** Today a resolved comment's actions collapse to Delete
(`Threads.tsx:115-123`) — which also means a reviewer who disagrees with an agent's
"skipped" verdict on their *own* comment can't re-queue it. The rule becomes: resolved
comments keep their buttons in all cases — in particular **Send now / re-queue** stays
available. That single UI rule unjams hotspots (agree with one → queue it for the
batch with one click) and fixes the existing re-queue gap, with the invariant intact:
nothing agent-authored ever enters the batch without a human click.

Hotspot comments carry a **severity badge** on the card (driven by a new optional
field on `Comment`) so they don't read as already-handled threads (Decision 6).

This is where "the NUL separator makes git treat approvals.ts as binary" belongs —
on the line, with a thread — instead of mid-paragraph in section prose. Prompt rule:
"risks and notable details go in `hotspots` anchored to the exact spot, NOT in the
narration; the narration explains, hotspots flag." The existing questions rule
(`prompts.ts:94`) currently ends "…those belong in the section narration" — it is
rewritten to point at `hotspots` instead (A10).

### A5. `verify` hints per section

```ts
// on wireSection
verify: z.string().optional()   // a command to run or behavior to poke
```

Rendered as a copyable chip. Turns passive reading into active review. Prompt: "when
a section's behavior can be checked in under a minute (a test file to run, a command,
a UI action), say how; else omit."

### A6. planMap grounding

`planMap.acceptance` entries gain an evidence anchor:

```ts
acceptance: z.array(z.object({
  text: z.string(),
  met: z.union([z.boolean(), z.literal('partial')]),
  source: z.object({ path: z.string(), line: z.number().optional() }).optional()
}))
```

Review 7 has five `"partial"` verdicts the reviewer must take on faith; with `source`
they're clickable claims. **`source` may cite an artifact OR a changed file**
(Decision — the draft restricted it to artifacts, but acceptance evidence
overwhelmingly lives in code and tests: "met, because this test exercises it").
Both anchor kinds already exist in `CommentAnchor` (`artifact` and `diff`/`file`).
Validation: `source.path` must be in the review's artifacts ∪ the diff's files, else
nulled with a warning. planMap otherwise unchanged — it is the educational core and
the sharpest-performing part of the current output alongside `questions`.

### A7. Cuts

| field | evidence | disposition |
| --- | --- | --- |
| `plainNotes` | 1/37 fill; never prompted; superseded by anchored blocks | **delete** (renderer pass-through dies at `SectionView.tsx:176`) |
| `insight` | expressible without a diagram; caption belongs to the diagram | **fold into `diagram.caption`** |
| `order` | redundant with array position on the full path; model fills a number, `validate.ts:54` sorts by it, nothing else reads it | **delete; array order is the order.** The scoped patch loses its placement signal with it — replaced by `afterSectionId` (see below) |
| `desc` | reads as "Review this first because…" meta-commentary duplicating summary rationale and `what`'s first sentence; rendered at `SectionView.tsx:53-55` | **delete; the first (unanchored) narration block carries the role.** Blocks are individually commentable, strictly better than `desc`'s separate commentability. Collapsed-section sub-line and `get_review` updated (A1, B3) |

**`afterSectionId` (Decision).** Deleting `order` is free on the full-generation path
(the sections array is complete; its order is the order) but the scoped patch is
*sparse*: a brand-new section arrives alone in `revisedSections`, and today `order` is
its only placement signal (`prompts.ts:262`; `splice.ts:114-116` sorts by it, and
`splice.ts:87-88` keeps revised sections in their prior slot via it). Replacement:
new sections in the scoped patch carry `afterSectionId: z.string().optional()` —
"place me after section X"; absent = append at end. Id-anchored placement is more
natural for a model than inventing a consistent number, and validation is direct:
unknown `afterSectionId` → warn, append at end. Splice changes: revised sections keep
their prior slot by position (the `inOrder` walk already iterates `prior.sections` in
order); the final sort-by-`order` is replaced by insert-after logic; `mergeAnnotations`
drops its sort (`validate.ts:54`) and trusts array order.

**Alternative considered — keep `order` on the scoped patch's sections only:**
rejected; numeric order against a list the model sees only as prose is exactly the
fill-a-plausible-number reflex being cut, and revised sections would carry a
meaningless required number. **Alternative — keep `order` everywhere:** rejected;
preserves a dead field on the main path to serve an edge case on the patch path.

`title`, `summary`, `questions`, `artifactPaths` unchanged.

### A8. Wire schema shape and constraints (rewritten for the post-ACP world)

The constraints comment at `schema.ts:4-9` describes the deleted SDK validators
(Claude `prefixItems`, OpenAI strict mode) and is **rewritten as part of this work**.
The actual constraints now:

- **zod is the sole validator**, applied client-side to schema-in-prompt output
  (`acp.ts:96,111` append `structuredEpilogue`; one repair turn on failure).
- **`.optional()` is allowed and preferred** for fields whose absence is the common
  case (`anchor`, `diagram`, `contrast`, `verify`, `sub`, `endLine`, …): the sparse
  output becomes the cheapest output, and omission no longer burns the repair turn
  (principle 3).
- **Keep shapes prompt-friendly**: flat objects over unions (A1), arrays over records,
  no tuples. The `DiagramNode` tuple type (`shared/types.ts:73`) dies with the tuple
  mapping in `sectionFromWire` (`schema.ts:98`); nodes stay objects end-to-end.
- **Schema size is a live cost**: the schema is prompt text and v2 is bigger; the
  repair-turn rate is one of the Stage-1 measurements.

Prompt-schema parity becomes a test that cannot pass vacuously: `buildReviewPrompt`
references every schema property **as a quoted literal** (`"why"`, `"anchor"`, …) —
the existing prompt already uses this convention ("desc", "what", "diagram") — and a
unit test asserts every property name in `reviewWireSchema` appears quoted in the
prompt text (the `plainNotes` lesson, mechanically enforced; bare-word matches don't
count).

### A9. Validation extensions (`validate.ts` / merge step)

`mergeAnnotations` keeps its file-set core (exactly-once assignment, stray sweep,
unknown-file drop). Its minted "Other changes" section (`validate.ts:44-52`) is
updated to the v2 shape (one unanchored narration block, no `desc`/`order`). All
additions warn-and-degrade rather than fail, and ride the existing `loadWarnings`
surfacing path.

**Stage 1 — integrity:**

1. **Block anchors**: an anchor whose `file` is anywhere in the diff → **kept**, even
   when the file belongs to another section (cross-references are legitimate teaching;
   the validator must not be stricter than the focus pathway it feeds). File not in
   the diff at all → de-anchor (keep text), warn. Line outside every rendered hunk →
   keep, `notInDiff`-style click-degrade to file focus (A1).
2. **Diagram integrity**: node anchors normalize/degrade like block anchors. Edges
   referencing unknown node ids → drop the edge, warn. Cycles detected at merge →
   warn (renderer falls back to node-list layout, A2).
3. **Hotspots**: file not in the diff → drop, warn. Anchors stamped at merge (A4).
4. **planMap `source`**: path not in artifacts ∪ diff files → null it, warn.

**Stage 2 — behavioral (measurement-gated):**

5. **Diagram budget**: more than 2 diagrams → keep the **first 2 by section order**,
   drop the rest, warn. Section order is the model's own attention-payoff ranking
   (`prompts.ts:89` orders sections "by where the reviewer's attention pays off
   most"), a far better usefulness proxy than the draft's add+del churn — the good
   quarter of stored diagrams are small tricky lifecycles, while high-churn sections
   skew mechanical.
6. **File-inventory heuristic**: node labels ≈ section file basenames (>50% of labels
   case-insensitively match a filename in the section) → drop the diagram, warn.
7. **Caption-confetti warning**: >80% of a section's blocks anchored and averaging
   under one sentence → warn only, never drop (Decision 15).

### A10. Review prompt rewrite (`buildReviewPrompt`, `prompts.ts:50-97`)

Structural changes, in the order they'd appear:

1. Narration instructions replace steps 2/3: blocks, continuity rule, reading-order
   rule, variable depth, first-block-as-desc.
2. Diagram budget + criteria + named anti-patterns (A2). The current
   "Optionally add a diagram: 2-5 nodes [label, kind, sub]" (`prompts.ts:91`)
   describes a **tuple** while the wire wants objects — dies in the rewrite.
3. Hotspot extraction rule (A4): risks out of narration, into anchored hotspots —
   **and** the questions rule (`prompts.ts:94`) is rewritten: "Do NOT put bugs,
   inconsistencies, or risks here — those belong in `hotspots`" (it currently says
   "…in the section narration", which A4 contradicts).
4. `contrast` and `verify` one-liners (A3, A5).
5. planMap `source` instruction (A6).
6. **Update-pass instructions land in both prompts, weighted to the scoped path**:
   `buildScopedUpdatePrompt` is the primary drift path now — `renderPriorSection`
   (`prompts.ts:170-180`) serializes prior sections' blocks (indexed, so "preserve
   prior blocks verbatim where their anchored code is untouched" is followable), and
   its step list gains that preservation rule plus `afterSectionId` for new sections
   (replacing "an `order` where it belongs", `prompts.ts:262`). The full-generation
   fallback's update block (`prompts.ts:69-75`) gains the same block-preservation
   sentence.

## Part B — Tool layer

### B1. Merge `focus` + `tour` → one `point` tool; add ranges

One pointing tool, 1–8 stops, each stop `{ target, note? }`; `target` gains optional
`endLine` on the diff arm (today `focus` takes a single line while explanations are
almost always about a hunk or function body; `tour` requires 2–8 stops,
`tools.ts:59-64`). Renderer shows a chip for one stop and the walkthrough card for
several — both renderers exist.

Rationale: `CHAT_TOOL_POLICY` spends two bullets teaching the model when to use
which (`prompts.ts:18-19`) — the tell that they're one concept at different arities.
Fewer tools, better selection under pressure, and half the channel confusion
disappears when there is only one way to point.

Compatibility: persisted `AgentAction`s of kind `focus`/`tour` keep rendering forever
(renderer keeps both branches); only the tool surface offered to engines changes.
`AUTO_ACCEPT_TOOL_NAMES` (`tools.ts:332`) swaps the two names for `point` — the
hand-maintained-on-purpose guard (`assertAutoAcceptCoverage`) fails loudly until it's
updated, which is the intended workflow. Naming decided: new name `point`, min 1 stop
(Decision 7).

### B2. `get_review_progress` (new tool)

Read-only; returns compact JSON: viewed files (`viewed_files`), reviewed sections
(`reviewed_sections`), open/queued comment counts, and the current drift summary
(Decision 16: included — read-only and cheap, and it lets the agent say "the review
is 2 commits stale — want an update pass?"). Auto-accept-safe (reads only Limn DB
state); added to `AUTO_ACCEPT_TOOL_NAMES`.

Unblocks calibration: "what should I look at next", skipping already-viewed
material, and making `suggest_mark_viewed` smarter (never suggest already-marked
files). The channel policy (B4) tells the agent to call it before proposing any
reading order.

### B3. `edit_review` v2: block addressing + planMap status

- Field enum (`tools.ts:83-87`) evolves: `title | summary | section.block |
  section.contrast | section.verify` — `section.block` takes `sectionId` +
  `blockIndex` + new text (and an `insert`/`delete` op; exact shape at
  implementation). `section.what`/`section.desc` die with the fields.
- `get_review`'s slim payload (`tools.ts:279`) drops `desc`/`what` and returns each
  section's blocks as an indexed text array — the read counterpart the block
  addressing needs.
- New dedicated tool `update_plan_status` (Decision 11 — separate from `edit_review`:
  different invariants — verdict transitions, note required — and the action renders
  distinctly): after a batch turn fixes code, the agent flips an acceptance criterion
  `partial → true` with a note. Today the five "partial" verdicts in review 7 would
  go stale forever. Emitted and persisted like other review edits (auditable); added
  to `AUTO_ACCEPT_TOOL_NAMES` (mutates review metadata only).
- `buildAnswerPrompt`'s field list (`prompts.ts:285`) updates to match.

### B4. Channel discipline

**`CHAT_TOOL_POLICY` is rewritten** (Stage 1) from per-tool "always" rules to a
channel-selection rule:

> Choose the one channel that fits your answer, then stop:
> - A question about the code → answer in prose, with at most **one** `point` call
>   at the key location.
> - "Walk me through X" / anything spanning locations → the multi-stop `point` **is
>   the answer**; explanation goes in stop notes; prose is one framing sentence.
> - Discussion of an existing comment → `reply_to_comment`/`resolve_comment` **is
>   the answer**; don't restate it in prose.
> - A bug noticed in passing → one `add_comment` at the spot; one prose sentence
>   saying you left it.
> Never state the same content in two channels. Chips carry locations — don't
> repeat `file:line` in prose next to a point call. Call `get_review_progress`
> before proposing what to read next.

**Batch prompt dedup** (Stage 1): `resolve_comment`'s note *is* the reply for the
common case. `reply_to_comment` is reserved for genuine back-and-forth (a
counter-question, a disagreement). The closing "2-3 sentence summary"
(`prompts.ts:148`) becomes "one sentence, only if something doesn't fit any resolve
note." Renderer prerequisite (Decision 9: adopted): `resolution.note` renders as a
reply-styled entry in the thread, not only as verdict metadata.

**Tool descriptions get exclusions** (Stage 1). Each description states its condition
*and* its exclusion: `point` — "when one call covers the locations, don't also point
at them individually"; `suggest_mark_viewed` — "at most once per turn, only after the
reviewer signals understanding" (replacing "don't wait to be asked",
`tools.ts:172-180`); `add_comment` — "for findings, not for restating your chat
answer".

**Host-level enforcement** (Stage 2, measurement-gated): the host sees every call in
a turn (`createToolHost`), so it can enforce deterministically what prompts state
probabilistically:

- a second `point` with the **exact same target set** as an earlier `point` this turn
  → error result: "already covered by your walkthrough — don't re-point";
- a second `suggest_mark_viewed` in one turn → error result.

Dedup strictness decided (Decision 8, resolving the draft's internal contradiction):
**exact-duplicate rejection only** — zero false positives; tighten to coverage-based
if measurement shows noise persisting. Error text teaches mid-turn (the model reads
tool results). Rejected alternative: renderer-side dedup (suppress chips duplicating
tour stops) — treats the symptom, and the transcript/persisted actions stay noisy.

**Why this shape:** the "use your tools actively" pressure exists because an earlier
version under-used them; adverb-nudging overshot. The stable fix is structural (one
pointing tool, resolve-note-as-reply, host dedup) — the redundant combination
becomes inexpressible rather than discouraged.

## Goals / Non-goals

**Goals**

- Narration that reads in the order the code should be read, at variable depth, with
  every focused claim one click from its code — and drift-stamped from day one.
- Diagrams only where a mechanism is genuinely non-obvious, structurally honest
  (edges), and clickable.
- Risks anchored as comments, not buried in prose — and actionable: one click queues
  a hotspot for the batch.
- Chat/batch turns that pick one channel and stop; no content stated twice.
- Every schema field prompt-argued, clickable, and checked where cheap (quoted-literal
  prompt-parity test, integrity gates); behavioral gates only after measurement.

**Non-goals**

- No bidirectional diff↔narration highlight in v1 (blocks are click-to-focus only).
- No block-level scoped-update patch format (blocks ride inside `revisedSections`;
  block-level patching is a measurable follow-up once staleness flags exist —
  Decision 13).
- No changes to comment drift *mapping* (comment-anchoring owns it; this spec only
  mints the same stamps).
- No quiz/"check my understanding" mode — a candidate follow-up once
  `get_review_progress` exists, out of scope here.
- No engine-specific prompt forks (Decision 10: the pre-ACP gradient may not survive
  the migration; re-measure first).

## Compatibility & migration

- **Stored annotations (v1)**: six reviews exist with `what`/`desc`/`order`/
  `plainNotes`/`insight`/tuple diagrams. On-load adapter in `loadReviewState` mapping
  v1 → v2 in memory (Decision 14 — no DB migration; new generations persist v2):
  `desc` → first unanchored block; `what` → following unanchored block;
  each `plainNotes` entry → a file-anchored block appended; `insight.caption` →
  `diagram.caption`; tuple nodes → object nodes (`''` kind → `'plain'`, no
  anchors/edges, chain edges synthesized from array order so old diagrams render
  identically); `order` dropped.
- **Scoped-update pipeline (this spec lands second and owns these changes)**:
  - `scopedReviewWireSchema` inherits blocks automatically (reuses `wireSection`,
    `schema.ts:58-67`); `sectionFromWire` (`schema.ts:90-102`) is the single seam
    where the anchor normalizer and object-node mapping land — both paths get them
    for free.
  - `renderPriorSection` (`prompts.ts:170-180`) serializes blocks indexed;
    `buildScopedUpdatePrompt` gains block preservation + `afterSectionId` (A10.6, A7).
  - `splice.ts` placement moves from sort-by-`order` to positional + insert-after
    (A7); its handshake/garbage guards are untouched.
  - `mergeAnnotations`'s "Other changes" minting goes v2; its sort dies (A9 preamble).
- **comment-anchoring (landed)**: block/node/hotspot anchors mint the same

- **FakeEngine / fixtures**: `fake.ts` and test fixtures produce v1 shapes; update

  describe the schema-in-prompt reality (A8).

## Failure modes

- **Caption confetti**: blocks degenerate into disconnected captions → continuity
  rule in prompt (Stage 1); the >80%-anchored/short-blocks validator warning is
  Stage 2, warning-only (heuristic; never drops content).
- **Repair-turn churn**: v2's bigger schema raises parse-failure odds → optionals
  make sparse output cheap; repair-turn rate is a Stage-1 measurement with the
  option to trim fields if it spikes.
- **Anchor rot on drift**: solved at birth — block/node/hotspot anchors carry
  `AnchorStamp`s and ride comment-anchoring's mapping; unresolvable anchors degrade
  to file-level focus at load.
- **Over-gating diagrams**: the Stage-2 budget cap drops a genuinely useful third
  diagram → warnings surface which were dropped; the reviewer can ask in chat for a
  `point` walkthrough covering the same need interactively.
- **Host dedup false positives**: exact-duplicate-only rejection makes these
  near-impossible by construction; if a model legitimately re-points (reviewer asked
  again), the error text steers it to prose referencing the earlier chip.
- **Merged `point` regressions**: engines might point less without focus/tour-shaped
  tools → fill-rates of persisted actions are part of the measurement gate; the
  channel-selection prompt names `point` explicitly in every branch.
